Atelier

A studio of AI perspectives that draw your software. Each one has a point of view, a kit of Python drawing tools, and eyes to look at what it drew. You bring a brief; they bring the sketches, the arguments between them, and the gaps they found.

github.com/mjohnson139/atelier · roadmap · MIT

The idea in three parts

The artist-profile experiment worked because of three things together: a persona with taste, real tools to make marks, and the ability to look at the result and try again. Atelier keeps all three and points them at software design.

A perspective, not a promptEach profile says what it cares about, what it ignores, its vocabulary and its favourite forms. The architect draws boundaries and failure paths. The tester draws risk.
A drawing kitPython tools that render declarative specs to SVG and PNG: graphs, sequences, wireframes, state machines, heatmaps. One free-hand canvas for anything the kit can't draw.
EyesEvery render comes back as an image. The persona critiques its own drawing against a rubric and revises, up to three passes. This is where quality comes from.

One rule holds it together: one design model, many views. The perspectives all draw from a shared model of the system (actors, components, flows, states, risks). When two views disagree, that disagreement is the most useful thing the studio produces.

The studio

Four perspectives draw. A curator runs the session and compares their views. These map loosely onto the 4+1 architectural view model, with the tester playing the scenarios view.

Designer

sees the system from the person using it

Cares about
User flows, every screen state (empty, loading, error, success), hierarchy, copy, what the user has to remember.
Draws
Flow maps, low-fi wireframes, a state grid per screen, journey maps with emotional dips.
Kit
draw_wireframe, draw_flow, draw_state_grid, draw_journey
Asks others
"Which of my error states has no path in your diagram?"

Architect

sees boundaries, data and failure

Cares about
Containers and their contracts, where data lives, trust boundaries, what happens when each dependency is slow or gone.
Draws
C4 context and container diagrams, sequence diagrams with failure branches, data-flow with trust zones, deployment maps.
Kit
draw_c4, draw_sequence, draw_dataflow, draw_deployment
Asks others
"Which of these boxes does your code actually depend on?"

Implementer

sees modules, types and the order to build them

Cares about
Module boundaries, interface contracts, dependency direction, pure versus effectful code, the smallest buildable slice.
Draws
Module dependency graphs (from real code via AST when a repo is given), type and contract cards, call graphs, a build-order plan.
Kit
draw_modules, draw_contracts, draw_callgraph, scan_repo
Asks others
"Your diagram has an arrow my code would need a cycle to honour."

Tester

sees where it will break

Cares about
States and transitions, edge cases, likelihood times impact, which risks no test covers, the shape of the test suite.
Draws
State machines with a path-coverage overlay, risk heatmaps, boundary-value grids, a test pyramid against the real inventory.
Kit
draw_state_machine, draw_heatmap, draw_boundaries, draw_pyramid
Asks others
"This transition exists in two views and is tested in neither."

Curator

runs the session; the only one who edits the model

Does
Turns your brief into the starting model, briefs each perspective, merges their proposed model changes, cross-examines the views and hangs the final board.
Produces
The board (all views on one page), a findings list (contradictions, gaps, risks), and draft GitHub issues for the ones worth doing.

How a session runs

  1. Frame. The curator turns your brief (or a repo plus a question) into a first model and a rubric for this session.
  2. Draw. The four perspectives run in parallel. Each writes a spec, renders it, looks at the PNG, scores it against its rubric, and revises. Three passes at most.
  3. Propose. A perspective never edits the model. It returns its views plus a list of proposed model changes, each with a reason.
  4. Cross-examine. The curator lines the views up against the model and each other: states with no path, boxes with no code, transitions with no test, flows that cross a trust boundary unannounced.
  5. Hang the board. One HTML page with every view, the findings, and draft issues. Specs sit next to images, so every drawing can be re-rendered and diffed in a PR.

The drawing kit

A small Python package, atelier_kit, served to the perspectives as a local MCP server. Tools take a declarative JSON spec, render locally, and return the image so the model can see it. Declarative specs keep drawings reproducible and reviewable; the free-hand canvas keeps the room for invention that made the artist experiment interesting.

Every tool writes views/<perspective>/<name>.{spec.json,svg,png}. A golden-image test suite renders each spec in kit/tests/specs/ and compares against committed output, so a kit change that moves pixels shows up in review.

A perspective profile

Profiles are Claude Code agent files, so the studio runs inside Claude Code itself. The body is the persona; the frontmatter pins the model and the tools.

---
name: studio-architect
description: Draws the system's boundaries, data flow and failure paths
  from the shared design model. Use in an Atelier session.
model: sonnet
tools: Read, Glob, mcp__atelier_kit__*
---
You are the studio's architect. You see containers, contracts, where
data lives and what happens when a dependency is slow or gone.

You ignore: colour schemes, copy, button placement, test counts.
Your forms: C4 context and container, sequence with failure branches,
data-flow with trust zones. Prefer one clear diagram to three busy ones.

Loop: write a spec, render it, call look, score it on the rubric
(legible at phone width? every arrow labelled? failure paths shown?
matches the model?), revise. Stop after three passes or a 4/5 on every line.

Never edit model/. Return: views drawn, proposed model changes with a
reason each, and questions for the other perspectives.

Where it runs

1. Inside Claude Code v1, recommended

Perspectives are .claude/agents/studio-*.md (the studio- prefix keeps them apart from the dev team's implementer, mechanic and reviewer), the kit is an MCP server in .mcp.json, and an /atelier skill runs the session as orchestrator. No infrastructure beyond a Claude subscription, and it works on any repo you open, locally or in a cloud session.

2. A headless CLI on the Claude API v2

atelier run brief.md, built on the SDK's tool runner with the same kit and profiles. Lets a GitHub Action redraw the board when a PR changes architecture. Pay-per-token, so it waits until v1 has proven the profiles.

3. Managed Agents later

A scheduled "drift review" that redraws views from main every week and opens an issue when the code and the drawings disagree.

Model choices

Borrowed from Words & Waffles: the expensive model thinks, plans and reviews; cheaper models do work that can be fully specified. Drawing is design work, so the perspectives get more model than an implementer would, and the article's model is kept for the passes where taste shows.

How it is built

Atelier is developed by AI agents under one owner, with the Words & Waffles way of working adapted (dev process):

  • Issues are the queue. Epics with ordered sub-issues; titles and labels use epic, feat, fix, chore, docs. Each session starts from a prompt that names one issue.
  • Run contract. A session implements, reviews, opens the PR and babysits CI. The owner merges and makes product calls.
  • Delegation. implementer, mechanic and reviewer agents with pinned models, and the same brief template.
  • Handoff and compounding. The write-handoff skill, docs/solutions/ for investigations, docs/decisions.md for product decisions.
  • Hard lines, new ones included: rendering is local (no Kroki, mermaid.ink or other render hosts); a perspective never edits the model; every image is committed next to the spec that made it; no secrets; make verify (ruff, mypy, pytest, golden images) before every push.

Roadmap

Each step is a GitHub epic with ordered sub-issues. The first subject to draw is Words & Waffles itself, because its owner already knows what the right drawings look like.

  1. Foundation. Repo, AGENTS.md, dev process, agents, make verify, CI.
  2. Kit v0. draw_graph, draw_state_machine, draw_heatmap, look, the MCP server, golden tests.
  3. One perspective, end to end. The architect draws W&W from a hand-written model, with the look-and-revise loop. This is where we learn whether the idea works.
  4. The studio. All four profiles, draw_wireframe and draw_sequence, the /atelier skill, parallel runs, compose_board.
  5. Cross-examination. The curator's contradiction checks; findings become draft issues.
  6. Grounded in code. scan_repo: the implementer and tester read a real repo and its tests.
  7. Headless. The API CLI and a GitHub Action that redraws the board on PRs.
